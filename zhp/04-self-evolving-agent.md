## 1. 意图（用户原话的还原）

> 做一个可自我审视、自我迭代的 agent。可以 on-the-fly 改自己，并热更新，也可以自我重启。

拆成三个可验证的能力：

1. **自我审视**：agent 能读到自己的行为记录（prompt、工具调用、轨迹、失败），并据此提出对自己的改动。
2. **自我修改 + 热更新**：改动能落地，且尽量不中断当前会话就生效。
3. **自我重启**：当改动的模块只能在启动时加载时，agent 能主动完成一次进程替换，并在新进程里接着干。

这不是"让 agent 写代码"的普通任务，而是**让 agent 的改动作用于 agent 自身**，因此失败模式和普通开发完全不同——改坏了，验证者也就没了。

---

## 2. 设计目标与非目标

### 目标

- G1：改一个插件 → 自动构建 → 自检 → 生效，全过程可审计。
- G2：需要重启时，agent 不停留在"请你手动重启"这一步，而是能自己触发。
- G3：任何一次改动都可一键回滚，且**回滚不依赖被改坏的进程**。
- G4：迭代有客观分数，不是自我感觉良好。

### 非目标（第一版明确不做）

- N1：不自动修改"成功的定义"或评测函数。
- N2：不允许 agent 修改 supervisor 和回滚逻辑。
- N3：不做无人工确认的连续多轮演化（先单步、可审计）。
- N4：不改模型权重——只改脚手架（prompt、工具、循环、插件）。

## 3. 现状盘点：DSH 已经给了什么

| 能力 | 现状 | 出处 |
|---|---|---|
| 热更新 | `dsh-hmr` 热替换模块、刷新配置、重组 profile | `packages/boot/hmr/` |
| 插件安装/启用 | `plugin_manager` 工具，有 HMR 时立即生效，否则返回 `restart-required` | `packages/boot/plugin-manager/` |
| 跨重启续命 | `dsh-goal` 的目标跨 turn / resume / fork / **进程重启**存活，默认 256 轮上限 | `packages/goal/goal/` |
| 会话持久化 | JSONL 压缩日志，可 resume；**中断的 turn 会被关闭，不会续跑** | `packages/session/session-persistence/` |
| 客观评测 | `benchmarks/` 已有 agent-continuation、session-corpus、terminal-io 等真实负载 | `benchmarks/` |
| 审视原料 | session log、trajectory、telemetry 全在磁盘 | `~/.dsh/sessions/` |
| 沙箱 | 工作区可写；core checkout 只读（写需一次性提权审批） | 实测 |

结论：**"自我审视"和"热更新"是拼装题；"自我重启"是结构题。**

## 4. 核心缺口：agent 不能是自己的父进程

服务 agent 的进程就是提供 Web GUI 的进程。杀掉它，执行环境消失，没有回来的路径。这不受权限影响——它处在因果链内部。

唯一的解法：**把重启的决策权交给 agent 改不到的一小块代码。**

```
┌─────────────────────────────────────────────┐
│  supervisor（外部，TCB，agent 不可写）        │
│  · spawn dsh                                │
│  · 轮询 health                              │
│  · 监听 restart-request.json（sentinel）     │
│  · 启动失败 → 自动回滚 last-known-good       │
└───────────────┬─────────────────────────────┘
                │ spawn
┌───────────────▼─────────────────────────────┐
│  dsh 进程（agent，随时可被替换）              │
│  · 改代码 / 构建 / 自检                      │
│  · 想重启 → 写 sentinel → 结束当前 turn      │
└─────────────────────────────────────────────┘
```

### 关键决策 D1：重启只发生在 turn 边界

不能在"边跑边重启"。因为会话层对中断 turn 的处理是**关闭**而非续跑（见 `session-persistence` README）。正确顺序：

```
写 restart-request.json + 把"下一步"写进 goal
  → 正常结束这一轮
  → supervisor 看到 sentinel，替换进程
  → 新进程 resume 会话，goal 仍在
  → 下一轮读回意图，继续
```

这样"自我重启"退化成一次普通的进程替换，不产生断裂。

### 关键决策 D2：sentinel 文件而非信号

agent 不去 kill 自己，只写下"请重启"这一事实。杀与不杀由 supervisor 决定。好处：

- agent 侧无自我终止的特权需求；
- 重启意图落盘可审计，能看到是谁在什么时候要求的；
- supervisor 可以在重启前做护栏检查（比如"上次启动 5 分钟内不得重启"，防止重启风暴）。

## 5. 自改用事务表达，不用编辑表达

**反模式**：改文件 → 重启。一次坏改就永久变砖。

**正确形状**（参考 A/B 分区、NixOS generations、Erlang release）：

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1. propose | 改动写进 `generations/<id>/`（git worktree，master 不动） | 丢弃，主线无感 |
| 2. build | 影子目录构建 | 丢弃，原进程继续跑 |
| 3. verify | 跑 benchmarks 子集 + 冒烟测试 | 丢弃，留下失败报告 |
| 4. activate | 更新 `current` 指针 + 写 sentinel | — |
| 5. restart | supervisor 起新代 | — |
| 6. health | 新进程 health 检查 | **自动回滚 last-known-good 再重启** |

**不变量**：磁盘上永远存在且只存在一个「已知可启动」的代际。这是系统不变砖的唯一保证。

## 6. 三个真正的坑

### 坑 1：自我打分 = 自欺（最高优先级）

如果 agent 既能改实现、又能定义"什么叫改好了"，它会迅速学会降低标准。这是自改系统的普遍死法。

**对策**：评测函数与 benchmark 集合必须位于 TCB 内，agent 不可写；只能读黑盒分数。所有"分数提升"必须能由 supervisor 独立复现。

### 坑 2：目标漂移

能改实现，不能改目标。goal 由人设定、由人确认完成。否则"自我迭代"退化为"自我漂移"。

### 坑 3：TCB 膨胀

supervisor + 回滚逻辑必须极小且 agent 完全不可写。一旦 agent 能编辑 supervisor，沙箱与回滚同时失效，系统退化为"无限制自改"。

建议 TCB 仅含：进程管理、health 探测、指针切换、回滚。**不含任何提示词、模型调用、业务逻辑。**

---

## 7. 三条硬约束（第一版就带）

1. **每轮只允许一个改动**，且必须是单文件或单参数级别；
2. **必须留下 diff + 改前改后的分数对比**，缺一不采纳；
3. **人类可一键回滚**，且回滚路径不经过 agent。

先可审计，再谈强大。

---

## 8. 路线图

### 第一步：最小闭环（只改插件，不碰 core）

- 工作区建 `evolve/` 插件：提供 `propose / build / verify / activate / rollback` 五个工具；
- 六十行 supervisor 脚本：spawn、health、sentinel、回滚；
- 验收：改插件 → 构建 → 自检 → 重启 → 新进程验证；**故意改坏一次，观察自动回滚**。

为什么先插件：插件坏了只是插件停掉，进程还在，agent 能当场看到报错并回滚。先证明回滚可靠，再谈动内核。

### 第二步：接客观评分

- 选 `benchmarks/` 中一到两个稳定子集；
- supervisor 独立跑分，agent 只读结果；
- 无分数提升的改动不允许 activate。

### 第三步：跨重启连续迭代

- 目标写入 `dsh-goal`；
- 每轮一个改动，记录 diff 与分数曲线；
- 设硬上限（轮数、时间、失败次数），超限自动停。

## 9. 开放问题（需要拍板）

1. **supervisor 用什么**：launchd plist / 一个 node 小进程 / 外部容器？launchd 最省事，但重启策略表达力弱。
2. **generations 用什么隔离**：git worktree 还是目录复制？worktree 省空间但共享 .git 锁。
3. **health 的判据**：HTTP 200 就够，还是要等某个 plugin ready 事件？前者快但可能假阳性。
4. **允不允许 agent 改 core**：第一版建议禁止；若允许，需要额外的人审闸门。
5. **失败预算**：连续 N 次 verify 失败是否自动停机并要求人介入？建议 N=3。
6. **审计载体**：现有的 session log 够不够，还是要独立的 `evolve/journal.jsonl`？建议独立，便于机器读取。

---

## 10. 一句话总结

**自我审视和热更新是把现有零件拼起来；自我重启必须外置一个 agent 改不到的 supervisor；而整个系统能否成立，取决于评测函数是否也在 TCB 里——否则它会学会骗自己。**
